# Electron Capability Integration Report — Phase 1.5

Date: 2026-09-15. Source commit: `011ca2e166ebc60d95283871d679c44e54b9e5c5`.

**Research and architectural planning only. No production code, tests, Electron features, or Phase 2 extractions were implemented.** This report supplements, rather than rewrites, the [Phase 1 baseline and roadmap](app-refactor-phase-1.md).

## 1. Executive summary

Electron should remain the platform foundation for windows, menus, dialogs, permissions, process isolation, accessibility transport and OS integration. SensibleMD must continue to own document authority, save/recovery decisions, semantic navigation, reading continuity, Markdown interpretation, and application focus behavior. Most of the existing custom document logic is specialization, not redundant infrastructure.

The most concrete replacement candidate is the custom window-bounds persistence in `electron/main.cjs`: the bundled documentation and installed Electron 44.1.1 typings contain `windowStatePersistence`. However, the bundled constructor reference marks it **experimental**, and its defaults include display modes that SensibleMD deliberately does not restore today. Evaluate it in a separate migration; do not replace the existing bounds code during the App refactor.

The strongest near-term native integration opportunities are deliberate application/context menus and editor spelling support. These are behavior changes, not mechanical extractions. Electron's spellchecker is enabled by default, but the installed CodeMirror implementation sets `spellcheck="false"`; SensibleMD does not override that. No spelling-suggestion/context-menu implementation was found. Native spelling would also introduce dictionary-policy, cross-platform and undo/caret questions.

The security comparison found useful existing protections and concrete gaps. Renderer sandboxing, context isolation, disabled Node integration, a narrow bridge, denied permissions, and blocked main-frame navigation/new windows are present. **IPC sender validation is not uniform**: ordinary document/state/recovery handlers do not enforce the same owner/main-frame checks as window-close completion. The default Electron application menu and default-enabled DevTools remain in use. `file://`, release fuses, URL validation, payload limits and release network behavior require separate attention. These findings do not justify silently changing behavior while extracting components.

Most Phase 2 steps remain appropriate. Modify the keyboard step's scope description so it is explicitly the current renderer keyboard adapter, not the permanent owner of all application shortcuts. Keep close/open/save actions transport-neutral and retain the existing native boundary. Add targeted characterization gates before affected steps. Do not reorder the whole refactor around speculative integrations.

## 2. Evidence, scope and classification

Primary evidence is the current source, [Phase 1](app-refactor-phase-1.md), bundled `docs/api` and `docs/tutorial`, installed dependency source/types, and project assurance/design guidance. Relevant source inspection included all Electron runtime files, preload declarations, packaging configuration, current editor configuration, App action/rendering paths, CSS preferences, existing boundary/scenario tests and packaged verification scripts identified in Phase 1.

The imported documentation directories have no pinned upstream revision established by this audit. API availability and suitability are therefore separate questions. Installed `node_modules/electron/package.json` reports **44.1.1**, and its typings confirm the window-persistence API. The [official Electron 44 announcement](https://www.electronjs.org/blog/electron-44-0) also identifies window-state persistence as an addition. That establishes availability, not behavioral compatibility or a release-quality recommendation. Other future APIs must likewise be checked against the release actually shipped.

A limited official-documentation web cross-check corroborated [window persistence](https://www.electronjs.org/docs/latest/tutorial/window-state-persistence), [spelling](https://www.electronjs.org/docs/latest/tutorial/spellchecker/), and [IPC sender guidance](https://github.com/electron/electron/blob/main/docs/tutorial/security.md). Bundled references below remain the main audit trail. Tutorials demonstrate capabilities; their examples are not production security policy or evidence of SensibleMD behavior.

Evidence labels used here:

- **Source-confirmed:** directly visible configuration, code, or absence of a handler in the inspected ownership path. This is not a claim that an exploit or every user-visible consequence was reproduced.
- **Existing test evidence:** bounded cases documented in Phase 1; these tests were not rerun in this documentation-only phase.
- **Requires verification:** packaged behavior, physical input, assistive technology, network traffic or a candidate's runtime compatibility not established by source alone.

The Phase 1 results remain historical baseline evidence: 225 tests passed, 70 TODO; build passed; lint exited successfully with warnings. **No new packaged, screen-reader, cross-platform or network tests were performed in Phase 1.5.** No overall security/accessibility/release PASS is claimed.

Each capability has one primary classification:

| Class | Meaning in this report |
|---|---|
| A | Already delegated appropriately; preserve and verify |
| B | Existing custom infrastructure plausibly replaceable; compatibility work required |
| C | Native foundation plus essential SensibleMD specialization |
| D | Keep custom; native equivalent does not provide the required semantics |
| E | Native opportunity that changes current observable behavior; separate authorization |

A C classification can include an implementation gap; it describes ownership, not completion. A missing feature is not B merely because Electron offers an API.

## 3. Current and recommended ownership maps

| Responsibility | Current owner | Appropriate foundation / continuing SensibleMD owner |
|---|---|---|
| Desktop shell, native title bar, minimize/restore/focus | Main `BrowserWindow`; `file-open-lifecycle.cjs` | OS/Electron manage windows; main decides application activation policy |
| Menus and standard edit/window roles | Electron default application menu; no custom context menu | Main builds native menus; OS roles perform standard operations; document command intent still reaches renderer orchestration |
| Editor text/selection/undo | CodeMirror in `MarkdownEditor.tsx` | Chromium input/IME + CodeMirror transaction/history; workspace buffer/source synchronization remains custom |
| Spelling | Electron default engine; CodeMirror disables content spellcheck | Electron/session/OS spelling engine; renderer editor opt-in and app policy; main suggestions/menu integration |
| Active document, save, recovery decisions | `DocumentWorkspace`, `DocumentBuffer`, recovery/close hooks | Renderer domain state; main enforces authorized path/write/storage operations |
| Native file selection and opening | Main dialog, identity/read/watch helpers; renderer activation | OS dialog supplies selection; main validates and owns capability; renderer chooses safe transition |
| Recent list | Main `recent-files.json`; renderer Home/workspace display | Keep app list for current semantics; OS recent surfaces can be a separately approved projection |
| OS file requests | Main single-instance/request lifecycle, preload callbacks, outer App acknowledgement | Preserve all three layers; Electron events do not implement dirty-state or commit acknowledgement |
| Window bounds | Custom main JSON/debounce/screen clamp | Candidate Electron persistence; main retains window identity and migration policy |
| Reader state/bookmarks/preferences | Workspace memory/localStorage and main document JSON | Chromium storage is a mechanism; semantic restoration, schema and ownership remain SensibleMD |
| Native appearance/AT bridge | Electron defaults | OS/Electron signals and accessibility tree transport; renderer semantics/theme/focus must be implemented/tested by SensibleMD |
| Security | Main window/session configuration, preload wrappers, CSP/sanitized renderer | Electron enforces configured boundaries; SensibleMD owns sender authorization, payload policy and file limits |
| Search/navigation/pagination/diagnostics | Renderer core modules/hooks | Keep custom semantics over Chromium layout/input; do not use browser history/find/print as replacements |
| External URLs | Reader link renderer + main navigation/window handlers → shell | Main remains final external-open policy; renderer resolves internal Markdown links separately |
| Clipboard | Chromium Clipboard API in App; native edit roles/CodeMirror | Preserve text-copy path; consider narrow main fallback only if real packaged failure is established |

The Electron `Session` (cookies/cache/storage/permissions/spelling/protocols), SensibleMD's ephemeral document `SessionId`, and filesystem authorization map are **three different concepts**. A persistent Electron partition neither authorizes a document nor resolves stale Save As completions.

## 5. Capability implications and integration gates

Each entry states security/privacy, accessibility, platform differences, test requirements, migration risk, and timing. “After refactor” is a default sequencing recommendation, not authorization.

**01 — Spelling.** Security/privacy: Hunspell dictionaries may download from the default Chromium/Google CDN on Windows/Linux; the upstream description says checking does not send typed text. Do not infer zero network traffic from disabled editor spellcheck or denied permission prompts. Accessibility: underlines are insufficient by themselves; keyboard-accessible correction matters. Platforms: macOS uses native language detection; Windows/Linux language selection and dictionary availability differ. Tests: packaged intentional misspellings, offline first run, language changes, code/URL contexts, large files, IME, correction/undo/caret/dirty/recovery across mode changes. Risk **high** for source/editor behavior. **Separate migration after editor C09/C15 characterization; never inside steps 9–10.**

**02 — Suggestions/dictionary.** Security/privacy: add/remove persists vocabulary; bundled session docs say macOS/Windows also affect the OS custom dictionary. Persistent sessions are required; this is not document-local storage. Do not put words in recovery JSON or transmit them. Accessibility: offer keyboard menu invocation, usable suggestions and predictable focus. Platforms: dictionary and menu behavior vary; macOS language APIs differ. Tests: right-click and keyboard opening, replace/undo once, stale menu after source/document change, dictionary add/remove/restart/failure, OS scope. Risk **high**. **Separate migration with 01**, not a new diagnostics responsibility.

**03 — Context menus.** Security: derive native items from trusted window/context information; validate any link target and do not include arbitrary path-opening or Inspect in production. macOS `menu.popup({frame})` can enable additional OS Writing Tools/Services; adding that can extend text-processing behavior and needs deliberate policy. Accessibility: native menus provide interaction mechanics but item names, enabled state, focus and keyboard triggers remain app obligations. Test selection/caret preservation, mouse/Shift+F10 where supported, menu dismissal, reader versus editor actions and packaged AT. Risk **medium/high**. **Separate migration after command factory step 2**, retaining palette/settings as separate interfaces.

**04 — AT bridge.** Security: no new bridge privilege is needed. Accessibility: automatic Chromium/OS tree exposure is the foundation, not proof that this document is usable. macOS/Windows explicit app toggle exists; Linux AT behavior requires its own validation. Test VoiceOver, Narrator and Orca with current controls/editor, virtualized content and hidden measurement. Risk **low** for preserving default; a forced override can affect performance and behavior. **Preserve during all steps; verification before UI extraction baselines, no new implementation by default.**

**05 — Semantic accessibility/diagnostics.** Security: keep Markdown sanitized and source ranges intact. Accessibility: app owns names, roles, landmarks, heading hierarchy, focus restoration, visible focus and diagnostic explanation; document diagnostics intentionally analyze authored content rather than platform configuration. Test keyboard/AT/zoom, checks panel filter and jumps, duplicate headings, oversized content and editor input. Platform differences are test requirements, not a reason to remove semantics. Risk **medium/high**. **Proceed with controlled components and existing diagnostics boundaries; do not replace them with Electron accessibility APIs.**

**06 — Appearance/motion.** Security/privacy: local OS signals need no filesystem or network expansion; only introduce main theme IPC if a user override must control native chrome too. Accessibility: Chromium may apply forced colors automatically even without app CSS; absence of custom handling is not proof it fails. Actual contrast and focus require testing. `nativeTheme.inForcedColorsMode` is Windows-specific; high-contrast/inversion APIs have platform qualifiers. Current manual reduced motion is not an OS-follow policy. Test live OS changes, explicit override precedence, reduced motion in JS scrolls, contrast, text scaling and pagination anchor continuity. Risk **medium/high** due geometry/persistence changes. **Separate migration after step 6; keep settings extraction controlled and unchanged.**

**07 — Isolation.** Security: preserve sandbox/context isolation/no Node; sandboxed preload has restricted imports and is not a place to relocate general Node modules. Accessibility: no direct feature substitution; broken preload can remove primary workflows. Platform sandbox behavior must be verified in each release package. Tests: actual preferences, renderer absence of Node, narrow bridge, offline packaged launch. Risk **high** if changed, **low** if preserved. **Boundary verification before lifecycle steps; no migration needed.**

**08 — IPC.** Security: explicit source-confirmed gaps are detailed in section 6. Electron cannot infer authorized frame/document from payload types. Accessibility: reject/failure must remain visible and not strand focus/work. Platform: validation must recognize only the owned packaged/development renderer; do not assume all `file://` origins are trusted. Tests: forged webContents, sibling/child frame, gone frame, stale session and malformed/oversized payload for every handler. Risk **high**. **Separately authorized hardening before adding menu/drop/theme/clipboard IPC; preserve current bridge in mechanical steps 12–18.**

**09 — Permissions/network.** Security: current deny-all is appropriate to current features; do not grant clipboard read/media/notifications to make tests convenient. Main network APIs, external browser launch and dictionary downloads are different channels. Accessibility: future capability failures need understandable feedback. Platform: first-run dictionaries, portals and native services differ. Tests: actual packaged network capture on clean profiles, blocked remote Markdown images, permission probes and offline behavior. Risk **high** when broadening permissions. **Preserve now; privacy gate before each new integration.**

**10 — Navigation/windows.** Security: top-level `will-navigate` is not a catch-all for subframes or main-programmatic loads. Current app does not intentionally embed remote frames; characterize attempted frames and hostile Markdown rather than inventing a currently exposed webview. Accessibility: blocked external navigation must not destroy reader focus/location. Test malformed targets, target blank, same-document anchors, previews and attempted frames in a package. Platform browser handoff varies. Risk **high**. **Preserve handlers during step 1; separate hardening before any new resource/embed protocol.**

**11 — External URLs.** Security: HTTPS scheme restriction is useful but not full parsed destination validation; no RCE reproduction is claimed. Decide URL parse/credential/malformed handling without silently banning ordinary public links or adding mailto. Handle shell failure observably. Accessibility: preserve link names and predictability of browser handoff. Test actual Reader/Preview differences, fragments/footnotes, encoded/uppercase URLs and launch failure on all OSes. Risk **medium/high**. **Add characterization before step 1; central policy improvement only in separate work.**

**12 — Dialogs.** Security: selection establishes user intent but does not solve stale requests, symlinks or special-file validation. Accessibility: native dialog interaction still needs keyboard/AT checks; parented-sheet behavior should not be changed while moving handlers. Platforms: Linux portals and dialog defaults differ; bundled docs note `defaultPath` limitations on older portal backends. Tests: cancel, inaccessible/missing file, dialog concurrency, filters and Save As failure. Risk **low** to preserve, **high** to change activation. **Steps 14–18 keep dialog operations in main and cancellation shape unchanged.**

**13 — Files.** Security: renderer session IDs do not replace main capabilities. Native dialogs do not supply atomic save, version guards or recovery semantics. MAS security-scoped resources address OS sandbox authority only; they are unnecessary for current non-MAS targets and require lifecycle design if adopted. Accessibility: errors and saved state must tell the truth. Platforms: rename/watch/permission behavior differs. Tests: real filesystem races, symlink/replacement, failure after write, stale main session, denied permissions. Risk **high**. **Keep custom domain plus main fs; no new file-access migration during steps 9–18.**

**14 — Recents.** Security/privacy: adding an OS recent entry exposes a path in another persistent OS surface; removing app recents would not necessarily remove OS history. Accessibility: native menu benefits do not eliminate Home list requirements. Platforms: macOS/Windows API; Linux current app list remains necessary. Tests: ordering/dedup, missing file, OS reactivation, clear policy, multiple instances and Home dirty protection. Risk **medium/high**. **OS projection after steps 2/18 in separate migration; do not replace the app list or positional IPC during step 18.**

**15 — OS open.** Security: retain main-owned requested path and request correlation; strengthen sender/frame checks separately. Accessibility: foreground/focus without unexpected mode/data loss. Platforms: macOS early open-file/Dock, Windows/Linux launch arguments and installed associations. Tests: real installed file activation and C14 three-request newest-pending sequence, before-ready, close preparation and commit acknowledgement. Risk **high**. **Preserve outer App/main ownership; do not defer necessary C14 merely because Electron emits the event.**

**16 — Drag/drop.** Security: obtain paths in preload and pass internally to validated main, avoid exposing paths to web content; `File` DOM objects cannot simply be sent to main through generic IPC. File-name filtering is not authorization. Accessibility: keep equivalent Open command; do not require drag as the only method. Platforms: dropped files, directory/symlink behavior, native drag images and editor text dragging differ. Tests: dirty document, multiple files, non-Markdown, crafted path, internal text moves/undo, restart recovery. Risk **high**. **Separate feature after activation/IPC characterization, never during native-open extraction.**

**17 — Application menus.** Security: remove release DevTools/reload policy deliberately, not by replacing the menu with null and losing standard roles. Accessibility: use roles for edit/hide/minimize; command enablement, labels and focus still need checking. macOS has a global menu; Windows/Linux have per-window presentation; Home must retain relevant commands. Tests: physical native menus, app unfocused/focused, dirty state, disabled Save, shortcut exactly once, CodeMirror undo and native close. Risk **high** because menu commands intersect save and lifecycle. **Separate migration after step 2; decide scope before step 11, not an automatic prerequisite for Wave A.**

**18 — Keyboard.** Security: native command dispatch should identify the owned workspace and send finite intent, not arbitrary function names/paths. Accessibility: retain editor consumption, composition and repeat rules; avoid global shortcuts that intercept other apps. Platform accelerator semantics and keyboard layouts differ; `CommandOrControl` alone does not solve all differences. Test real menu accelerator plus DOM/CodeMirror delivery to avoid double invocation; preserve C12/C15. Risk **high** for redistribution. **Modify step 11 description only; perform exact extraction unless a separate native-menu migration is explicitly selected first.**

**19 — Windows.** Security: keep untrusted content from creating privileged windows. Accessibility: native frame/OS window operations are valuable; no reason to introduce custom draggable chrome. Test hide/unhide, minimize/restore, Dock/taskbar, snapping and Linux compositor behavior. Risk **low** preserving current shell. **No replacement needed; keep main ownership.**

**20 — Close/quit.** Security/data integrity: native events cannot know pending save/recovery/version state. Quit currently bypasses the window guard; that is a separately recorded existing behavior, not fixed by using a menu role. Accessibility: dialog choices/focus and cancellation must remain usable. Platforms: Windows shutdown/logout does not promise the ordinary before-quit sequence; updater quit ordering also differs. Test native window close, Cmd+Q/app.quit, repeated requests, held writes, shutdown signals where possible; distinguish process death from cancellable close. Risk **high**. **Keep step 17 as Close Document only; separately design quit protection before public release or updater integration.**

**21 — Bounds.** Security: migrate only window geometry, never delete reader state. Accessibility: offscreen restoration and minimum size are correctness requirements. Platforms: mixed-DPI, monitor removal, Linux Wayland placement restrictions and no-display behavior need comparison. Native options are experimental; default display-mode persistence changes behavior. Tests: old JSON migration, bounds-only candidate, maximized/fullscreen exit, restart immediately after resize, damaged state, no intersection and tiny work area. Risk **medium/high**. **Separate evaluation after mechanical refactor; defer any new custom window-state extraction now.**

**22 — Clipboard.** Security/privacy: current explicit text write is narrower than privileged clipboard read; the deny-all session policy may interact with browser clipboard behavior and needs a real test. Accessibility: copied status and native edit interaction remain app responsibilities. Platforms: Linux selection clipboard and macOS find pasteboard are not the regular clipboard. Test plain source exactness, selected rendered text, failure feedback, cut/paste/undo, physical native menu. Risk **low** to preserve, **medium** to add fallback. **No replacement during command extraction; add a write-only bridge only for a reproduced need.**

**23 — Print/PDF.** Security: local export path needs a user-selected destination; no silent printing. Accessibility: PDF tagging/reading order must be validated; visual output is not proof of accessible PDF. Platforms: printer backend, paper and margins differ. Tests: complete source including offscreen pages, no measurement duplicates/UI chrome, links/footnotes/code/oversize, cancel/failure and exported tags. Risk **high**. **Separate feature after mechanical refactor; retain current measured pagination.**

**24 — Crash.** Security/privacy: dumps may contain document content; do not enable uploads by default. Accessibility: crash/recovery UI must explain available data without falsely promising all text survived. Platforms: renderer/main/GPU failure and OS termination paths differ. Tests: forced renderer termination, lost IPC, pending write, crash-loop prevention, last successful recovery generation and no unexpected network. Risk **high**. **Separately scoped resilience work before claiming recovery completeness; no automatic reload during refactor.**

**25 — Notifications.** Security/privacy: notifications can expose document names/content outside the window; main API is not governed simply by renderer permission denial. Accessibility: notifications may be suppressed; retain in-app live status. Platforms: Windows identity/registration, macOS permission/appearance, Linux desktop service differ. Test dismissal/focus/disabled notifications only if feature approved. Risk **medium**. **Currently unnecessary; no migration.**

**26 — Session storage.** Security/privacy: changing partition/origin changes access to localStorage, dictionaries and permission/cache state. `clearStorageData` is not a recovery migration. Accessibility: lost preferences affect use. Platforms: user-data location and OS dictionary integration differ. Tests: upgrade/restart, profile isolation and old-state retention. Risk **high**. **Preserve current session during step 16; future partition changes require explicit data migration.**

**27 — Protocol.** Security: serve only allowlisted packaged assets; reject traversal/encoded paths and do not use `bypassCSP`. Never turn the protocol into a general filesystem reader. Accessibility: broken assets/styles affect all UI. Cross-platform URL/path normalization and packaged ASAR paths need tests. Origin changes can hide legacy localStorage and alter CSP, clipboard and resource behavior. Risk **high**. **Separate security migration with storage plan and offline package tests; not during step 1 or 16.**

**28 — Updater.** Security/privacy: signed artifacts, trusted manifest/feed, network disclosure and rollback are release policy, not supplied entirely by the API. Accessibility: explicit update state and defer/restart controls. Platforms: built-in updater supports macOS/Windows mechanisms described upstream; NSIS compatibility requires separate assessment; Linux typically uses distribution/package-specific mechanisms. Tests: signature failure, interrupted update, held saves/recovery, cancel/defer and install/relaunch. Risk **high**. **Future release project, after quit/save guarantees and packaging decisions; no implementation now.**

**29 — Search/history.** Security: replacing semantic actions with URL navigation can invalidate the trusted renderer lifecycle. Accessibility: browser find does not provide the app's collection result explanation/focus behavior. Platform native find pasteboard might be supplementary, not a replacement. Tests: existing search/history/position C10/C11/C16. Risk **high** to replace. **Keep custom; never use native browsing history as the domain history.**

**30 — Domain reading/writing.** Security/data integrity: retain full-source sanitation and versioned writes; do not delegate save to a browser download or print pipeline. Accessibility: reading position, reachable oversize blocks and editor projection are app obligations. Platform layout differences require current geometry tests. Risk **high** if generalized away. **Proceed with existing semantic/core boundaries and characterization; no native replacement identified.**

**31 — Represented document.** Security/privacy: main selects the authorized path; renderer must not provide arbitrary represented filenames. Clear marker on Home/browser documents and update after Save As. Accessibility: native indicator supplements explicit saved state, not color/icon-only reporting. macOS-only APIs; other OSes need no imitation. Test clean/dirty/Save As/close and retained main authorization mismatch. Risk **medium/high**. **Separate feature after lifecycle characterization; no new dirty-state authority.**

**32 — Hardening.** Security: fuses are package-time settings; distinguish renderer DevTools from Node inspection/RunAsNode and ASAR integrity. Accessibility: removing default menu wholesale can remove native edit/window operations. Platforms/signing and ASAR support differ. Existing packaged scripts depend on debugging instrumentation; production fuse changes may require a separate test strategy. Tests: inspect actual packaged fuse bits/menu/launch arguments, offline launch and update/signature compatibility. Risk **high**. **Separate release-hardening work before public binary approval; never alter packaging as an incidental refactor.**

**33 — Offloading/secrets.** Security: a Node utility process is not a substitute for renderer sandboxing or an authorized index root; secret encryption has OS-specific protection/fallbacks. Accessibility/performance: measure typing/AT responsiveness before adding worker complexity. No current credential feature justifies safeStorage. Tests if later needed: source-version cancellation, crash cleanup, performance and key unavailability. Risk **high** for unnecessary ownership change. **Currently unnecessary; keep performance optimization and credential storage out of Phase 2.**

## 6. Security alignment findings

The [bundled security checklist](tutorial/security.md) and project [ELC-001–017 requirements](SENSIBLEMD_RELEASE_ASSURANCE_CHECKLIST.md) are separate from the blank [security audit checklist](security_audit.md). None is marked complete by this report.

### Existing alignment

- **ELC-001–004:** `createWindow` explicitly sets `nodeIntegration: false`, `nodeIntegrationInSubFrames: false`, `contextIsolation: true`, `sandbox: true`, `webSecurity: true`.
- **ELC-005–006:** no opt-in to insecure mixed content, experimental renderer features or extra Blink features was found. Preserve defaults; runtime verification is still required.
- **ELC-007:** `index.html` supplies restrictive script/default/object/base policy, limits images to self/data/blob and fonts to self/data. Styles allow inline styles; connect includes the development loopback WebSocket. This is a concrete policy, not a completed injection/network audit.
- **ELC-008–009:** main-frame navigation is prevented and new windows denied. HTTPS shell handoff is a separately reviewed action, not permitted renderer navigation.
- **ELC-012:** task-specific preload functions, no raw IPC/Node/fs/shell exposure, event objects stripped from callbacks, unsubscribe functions returned.
- Session check/request handlers deny permissions. Native path stays in main; direct-save authorization is selected from a main-owned session map. This is meaningful least privilege, although not every IPC caller is adequately authenticated.

Wave A need not wait for speculative new features; adding privileged APIs must wait for relevant boundary hardening.

## 7. Accessibility ownership review

### Platform-provided

Chromium/Electron supply the accessibility tree transport and OS assistive-technology integration, native dialog/menu mechanics, input/composition support and native appearance signals. Installed CodeMirror gives its content element textbox/multiline attributes. Those are useful foundations; the outer editor section's name is not by itself proof that the editable textbox has the correct accessible name in every AT.

### SensibleMD-provided

The app owns correct rendered headings, document/landmark structure, control names, target/source mapping, focus restoration, Escape behavior, search visibility separate from query, meaningful status, reading order, reachable oversized content, and the distinction between reader and writer interactions. The inert offscreen measurement subtree must remain absent from the accessibility tree. Native menus do not repair inaccessible custom panel controls.

### Authoring diagnostics

Markdown authoring checks inspect the document being written. They are not spelling, screen-reader integration, an accessibility-tree replacement or runtime app certification. Keep `accessibility-diagnostics.ts` and `AuthoringChecks` separate from any future spelling menu/session settings. Correcting a misspelled word is a source edit; changing diagnostic visibility is a view choice; neither should be reclassified as reader navigation.

### Testing rather than speculative implementation

Before adding forced accessibility toggles, generic focus frameworks or replacing CodeMirror, test the current package with VoiceOver, Narrator and Orca; keyboard-only controls, IME, zoom/text scaling and forced colors; native menu operations; modal dismissal; Read/Write/Split transitions; duplicated hidden measurement; and long/oversized documents. Native underlines, native menus, automated ARIA assertions and screenshot similarity do not replace these checks. All remain **NOT TESTED in this phase**.

## 8. Overlap and redundancy conclusions

1. **True substantial overlap:** custom window geometry persistence versus Electron's experimental persistence API. Evaluate compatibility; do not presume migration is simpler than retaining a small tested policy.
2. **Partial input overlap:** renderer application shortcuts and native menu accelerators. The opportunity is moving transport, not moving save/navigation authority to main. CodeMirror keys and modal Escape remain context-sensitive renderer behavior.
3. **Complementary, not duplicate:** app recents versus OS recent surfaces; Markdown diagnostics versus spelling; app metadata versus Electron session storage; document history versus URL history; measured reader pages versus print layout.
4. **Already native underneath:** dialogs, framed windows, browser clipboard and AT transport. Rewriting these as bespoke React/native bindings would add risk without a demonstrated benefit.
5. **Native API without replacement semantics:** dialogs do not save safely by themselves; `setDocumentEdited` does not own dirty state; crashReporter does not recover buffers; `findInPage` cannot search an unrendered collection; browser sessions do not authorize files.

## 10. Ordered integration roadmap — separately authorized work

1. **Review this report and accept boundary notes.** Preserve Phase 1 as the historical baseline. No production change in this step.
2. **Establish targeted packaged/native characterization.** N01–N06 for touched workflows; retain Phase 1 C01–C16. Record source-confirmed gaps separately from runtime failures. These tests may precede specific extractions without adding features.
3. **Prioritize explicit safety/hardening scopes.** IPC validation/payload policy, quit safety and release DevTools/menu/dev-mode policy should be considered before shipping or adding privileged integration. Each requires its own review, tests and behavior-change notes. Rebaseline related extraction work after a fix, rather than mixing diffs.
4. **Continue authorized mechanical Wave A/B work with amended boundaries.** Pure commands and controlled UI expose useful action ports. Preserve native roles/bridge/renderer key semantics during moves. Steps 12–18 remain individually gated.
5. **Native application/context menus, if approved.** First preserve standard roles and establish exactly-once command routing/enablement; then add context actions. Keep modal/editor keyboard handling in renderer. Decide which application accelerator has a single owner.
6. **Spelling/suggestions/dictionary, if approved.** Determine privacy/language/scope policy first; validate CodeMirror correction through normal source/undo/recovery behavior. Do not bundle native Writing Tools/cloud-connected OS features automatically.
7. **Appearance/accessibility integration, if approved.** Define system versus explicit preference precedence and persistence; verify live updates preserve semantic reading location and accessible contrast. Use native signals rather than a polling/theme-detection service.
8. **Evaluate native window-state persistence in isolation.** Confirm experimental API behavior on target platforms and old-state migration. Run one persistence authority at a time, preserve legacy JSON for rollback, and avoid native display-mode defaults that change current behavior. Reject migration if compatibility cost exceeds its value.
9. **Optional OS recents, represented-file marker and drag/drop.** Separate feature scopes, path privacy and activation/dirty guards. No app-recent-list replacement assumed.
10. **Separate packaged-resource/protocol and fuse project.** Coordinate origin/localStorage migration, CSP and production test tooling; verify final signed artifact. Do not change protocol just by copying a tutorial handler.
11. **Later resilience, printing and update projects when product scope requires them.** Crash detection is not recovery; print needs complete-document output; updates require signed distribution and safe quit. Native notifications, utility processes and secret storage remain unnecessary without a concrete requirement.

Steps 5–11 are independent product/release decisions, not a mandatory feature backlog for this refactor. Security/data-integrity findings should be prioritized by project assurance requirements, not by how much App code an integration removes.

## 11. Do not implement during the mechanical refactor

- Spellcheck enablement, correction menus, dictionaries, automatic correction or OS Writing Tools/Services changes.
- New application accelerators, changed keyboard ownership, global shortcuts, native context menus or default-menu replacement.
- Quit behavior changes, automatic crash reload/recovery, native edited markers or represented filenames.
- OS recent-list projection/replacement, new drag/drop or deep-link handlers, broader filesystem access or file filter changes.
- System-theme/motion preference behavior, forced-color redesign, new accessibility toggles or changes to diagnostic semantics.
- Window-persistence replacement, partition/storage migration, localStorage cleanup or schema changes.
- Custom asset protocol, permission grants, IPC contract changes, payload restrictions, fuses, signing or updater configuration.
- Native clipboard reads/fallbacks without need, notifications, printing/PDF, background services, credentials or dependency upgrades.
- Replacement of semantic history/search/navigation/pagination, DocumentBuffer, recovery or CodeMirror with similarly named native APIs.
