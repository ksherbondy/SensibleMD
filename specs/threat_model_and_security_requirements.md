# Accessible Markdown Reader & Editor
# Threat Model and Security Requirements

**Document type:** Security architecture specification  
**Status:** Working specification  
**Purpose:** Define the security boundaries, threat model, abuse cases, trust assumptions, mitigations, and validation requirements for a desktop Electron-based Markdown reader/editor that opens untrusted local Markdown, renders HTML-like content, follows links, loads local assets, supports custom CSS, and may eventually support extensions.

---

# 1. Purpose

The application must assume that Markdown files can be untrusted.

A user may open:

- files downloaded from the internet,
- README files from unknown repositories,
- documentation bundles,
- Markdown generated by third-party tools,
- maliciously crafted local files,
- files containing embedded HTML,
- files referencing remote images or links,
- collections containing path traversal attempts,
- documents containing malformed or adversarial syntax.

The application is a local desktop program with filesystem access. That makes security failures potentially more serious than in a normal browser tab.

The central security rule is:

> **Rendered document content must never inherit application privileges.**

A Markdown file may be allowed to influence how its own content is displayed, but it must not gain access to:

- Node.js APIs,
- Electron privileged APIs,
- arbitrary filesystem operations,
- shell execution,
- process control,
- credential stores,
- application secrets,
- unrestricted local-network access,
- arbitrary IPC.

---

# 2. Security Goals

The application should protect:

## 2.1 User files

Prevent:

- silent deletion,
- unauthorized modification,
- accidental overwrite,
- path traversal,
- writes outside user-authorized targets.

## 2.2 User privacy

Prevent:

- silent document exfiltration,
- silent remote requests,
- hidden tracking pixels where avoidable,
- accidental disclosure of local paths,
- leakage of clipboard or file contents.

## 2.3 Host system

Prevent rendered content from:

- executing shell commands,
- loading native modules,
- using Node.js directly,
- invoking arbitrary Electron APIs,
- spawning processes,
- escaping sandbox boundaries.

## 2.4 Application integrity

Prevent malicious content from:

- corrupting app state,
- poisoning persistence data,
- injecting privileged scripts,
- abusing IPC,
- altering settings outside intended flows.

## 2.5 User intent

Security-sensitive actions should be explicit.

Examples:

- opening an external URL,
- saving over a file,
- loading remote resources,
- enabling unsafe HTML,
- enabling custom CSS,
- installing extensions/plugins.

# 3. Trust Boundaries

Conceptually:

```text
+------------------------------------------------------+
|                    Operating System                  |
|                                                      |
|  +----------------+      +------------------------+  |
|  | Electron Main  |<---->|   Preload Bridge       |  |
|  | Privileged     | IPC  | Limited API Surface    |  |
|  +----------------+      +------------------------+  |
|          ^                         ^                  |
|          |                         |                  |
|          |                         v                  |
|          |              +------------------------+   |
|          |              | React Renderer         |   |
|          |              | Unprivileged UI        |   |
|          |              +------------------------+   |
|          |                         ^                  |
|          |                         |                  |
|          |              +------------------------+   |
|          |              | Rendered Markdown      |   |
|          |              | UNTRUSTED CONTENT      |   |
|          |              +------------------------+   |
|          |                                            |
|          +---------------- Filesystem ----------------+
+------------------------------------------------------+
```

Rendered Markdown belongs on the untrusted side of the boundary.

# 4. Threat Actors

Potential threat sources include:

- malicious repository authors,
- malicious downloaded Markdown,
- compromised documentation packages,
- malicious local users,
- accidental malformed content,
- malicious extensions/plugins,
- malicious CSS,
- hostile linked HTML,
- compromised remote assets.

The threat model should not assume that opening a `.md` file means the file is safe.

Important assets include:

application settings
bookmarks/history
accessibility settings
clipboard contents
OS credentials
SSH keys
browser/session data
environment variables

# 6. Electron Security Baseline

The application should follow current Electron security recommendations.

Core requirements:

```text
contextIsolation: true
nodeIntegration: false
sandbox: true where compatible
webSecurity: true
```

The renderer should not receive unrestricted Node.js globals.

Avoid:

```text
require(...)
process
fs
child_process
shell
ipcRenderer exposed directly
```

inside untrusted renderer content.

---

# 7. Main Process Responsibilities

The Electron main process should own privileged actions such as:

- file open/save dialogs,
- filesystem access,
- OS file association,
- shell-open external URLs,
- application lifecycle,
- secure settings persistence,
- native integration.

The main process should validate all requests received from renderer/preload.

Do not trust a request merely because it came through IPC.

---

# 8. Preload Bridge

The preload bridge should expose the smallest API surface practical.

Bad:

```ts
contextBridge.exposeInMainWorld("electron", {
  ipcRenderer
});
```

Better conceptually:

```ts
contextBridge.exposeInMainWorld("appApi", {
  openMarkdownFile,
  saveMarkdownFile,
  openExternalLink,
  readAllowedAsset
});
```

Each method should:

- have a narrow purpose,
- validate arguments,
- avoid generic command execution,
- return bounded data,
- reject unexpected paths/types.

---

# 9. IPC Requirements

| ID | Requirement |
|---|---|
| SEC-IPC-001 | Renderer must not receive raw unrestricted `ipcRenderer`. |
| SEC-IPC-002 | IPC channels must have specific names and purposes. |
| SEC-IPC-003 | Main process must validate message schema and argument types. |
| SEC-IPC-004 | IPC handlers must reject unexpected fields. |
| SEC-IPC-005 | File paths received through IPC must be normalized and validated. |
| SEC-IPC-006 | IPC must not expose arbitrary shell execution. |
| SEC-IPC-007 | IPC must not expose generic filesystem read/write methods unless constrained. |
| SEC-IPC-008 | Errors returned over IPC must avoid leaking sensitive internal state unnecessarily. |
| SEC-IPC-009 | Privileged operations should require explicit user action where appropriate. |
| SEC-IPC-010 | IPC handlers should be auditable and enumerable. |

# 10. Markdown Rendering Threats

Markdown may contain or generate:

- HTML,
- links,
- images,
- iframes in extensions,
- SVG,
- data URLs,
- CSS classes,
- raw attributes,
- script-like strings,
- event-handler attributes.

The application must treat parser output as data, not trusted HTML.

---

# 11. HTML Sanitization

If embedded HTML is supported, it must be sanitized before entering the DOM.

Dangerous constructs include:

```html
<script>
<img onerror="...">
<a href="javascript:...">
<iframe src="...">
<object>
<embed>
<form action="...">
```

Sanitization policy should explicitly define:

- allowed tags,
- allowed attributes,
- allowed URL schemes,
- allowed style behavior,
- whether SVG is allowed,
- whether forms are allowed,
- whether iframe/object/embed are prohibited.

A dedicated sanitizer should be used rather than handwritten regex sanitization.

---

# 12. Markdown Parser Security

The selected parser should be evaluated for:

- raw HTML behavior,
- unsafe link handling,
- malformed nesting,
- extension security,
- denial-of-service edge cases,
- maintenance health.

Do not assume CommonMark compliance implies security safety.

---

# 13. URL Scheme Restrictions

Links must validate schemes.

Allowed examples may include:

```text
https:
http:
mailto:
```

Local application navigation may include controlled file paths.

Dangerous or restricted schemes include:

```text
javascript:
vbscript:
data:
file:
shell:
```

`file:` handling should be tightly controlled.

---

# 14. External Link Handling

External links should not open inside privileged app context.

Preferred behavior:

```text
rendered link
   |
validate URL
   |
user activates
   |
main process / safe shell open
   |
default system browser
```

Requirements:

- validate scheme,
- do not pass arbitrary executable paths to shell,
- do not expose Electron internals to destination pages.

---

# 15. Remote Resource Loading

Markdown may reference:

```md
![tracking](https://example.com/pixel.png)
```

Remote resources can leak:

- IP address,
- timing,
- document-open event,
- potentially referrer-like context.

The application should define a policy.

Possible default:

```text
remote images disabled or privacy-gated
```

Alternative:

```text
remote images allowed with explicit user preference
```

At minimum, user should understand whether remote content is loaded.

---

# 16. Local Asset Loading

Markdown may reference:

```md
![diagram](../images/network.png)
```

The application should resolve assets relative to the document safely.

Requirements:

- normalize path,
- detect traversal,
- distinguish intended relative asset from arbitrary file access,
- avoid exposing unrelated sensitive files.

---

# 17. Path Traversal

Malicious link:

```md
![x](../../../../../../etc/passwd)
```

or Windows equivalent.

The application must not blindly resolve arbitrary relative paths for preview.

Potential policy:

- local assets may load only from:
  - current document directory,
  - explicitly trusted collection roots,
  - user-approved paths.

This policy should be configurable only with clear user intent.

---

# 18. File Read Boundary

A document should not gain arbitrary read access merely by linking to a path.

Distinguish:

```text
user explicitly opens a file
```

from:

```text
document silently references a file
```

The second should have stricter permissions.

---

# 19. File Write Boundary

Rendered content must never trigger writes.

Only explicit editor/application actions may write.

Requirements:

- Save requires active document context,
- Save As requires user path selection,
- no automatic write to link targets,
- no document-controlled output path.

---

# 20. Symlink Considerations

Filesystem checks should account for symbolic links.

A path that appears inside an allowed directory may resolve outside it.

Where local asset policies matter, compare resolved real paths rather than only string prefixes.

---

# 21. Custom CSS Threat Model

Custom CSS can affect:

- readability,
- visibility,
- focus,
- interaction,
- layout,
- pagination,
- potentially data exfiltration via remote URLs.

Threats include:

```css
background: url("https://attacker.example/track")
```

and selectors attempting to hide application UI.

---

# 22. CSS Isolation

Document CSS should be isolated from privileged application UI.

Possible strategies:

- Shadow DOM,
- scoped container,
- CSS sanitization,
- separate rendering context.

The document should not be able to style:

```text
application menus
settings dialogs
security prompts
file controls
```

---

# 23. CSS Remote URL Policy

Custom CSS should not silently load arbitrary remote resources.

Consider blocking or gating:

```css
url(https://...)
@import
```

Remote font/image loading should follow the same privacy policy as Markdown resources.

---

# 24. CSS Accessibility Safeguards

User accessibility preferences should be able to override document styles.

Examples:

- foreground/background,
- minimum font size,
- focus visibility,
- high contrast.

Document CSS should not permanently make content unreadable.

---

# 25. SVG Risks

SVG can contain:

- scripts in some contexts,
- external references,
- event handlers,
- foreignObject content.

SVG handling should be reviewed separately from ordinary raster images.

Options:

- sanitize SVG,
- render in restricted image context,
- disable unsafe inline SVG features.

---

# 26. Data URLs

`data:` URLs should be treated cautiously.

They can embed:

- images,
- HTML,
- SVG,
- scripts depending on context.

Policy should allow only explicitly safe MIME types if needed.

---

# 27. Clipboard Security

The app may copy:

- text,
- links,
- code blocks.

Requirements:

- reader copy should copy only requested content,
- clipboard reads should not occur without user action,
- clipboard contents should not be exposed to document scripts,
- copy operations should not silently add tracking metadata.

---

# 28. Drag and Drop

Dropped files must be treated as untrusted.

Requirements:

- validate file type,
- do not execute dropped files,
- do not treat dropped directories as trusted roots without user consent,
- normalize paths.

---

# 29. File Association Security

OS file association should only open the passed Markdown document.

Do not interpret filenames as command-line options or shell fragments.

Validate process arguments carefully.

---

# 30. Command-Line Launch Arguments

If the app supports:

```text
app file.md
```

then:

- parse args safely,
- do not shell-expand them,
- do not execute them,
- distinguish flags from file paths robustly.

---

# 31. Shell Execution

The application should not need shell execution for core reading/editing.

Avoid use of:

```text
child_process.exec
execSync
spawn with shell:true
```

unless a narrowly justified feature requires it.

If ever required, document in an ADR and constrain inputs.

---

# 32. External Applications

Opening a URL or revealing a file in the OS should use safe, platform-supported APIs.

Do not construct shell command strings manually.

---

# 33. Persistence Security

Application state may contain:

- recent files,
- bookmarks,
- reading positions,
- custom profiles.

Requirements:

- treat persisted JSON as untrusted input on load,
- validate schema,
- tolerate corruption,
- avoid code evaluation,
- do not deserialize executable objects.

---

# 34. Settings Integrity

Malformed settings should not crash the app or disable security controls.

Security-critical defaults should fail closed.

Example:

```text
invalid setting for allowRemoteContent
```

should not silently become:

```text
true
```

---

# 35. Book Collection Trust

A directory-based book may contain many linked files.

Opening one file should not automatically trust the entire filesystem hierarchy.

Define collection root explicitly.

Potential flow:

```text
open chapter
   |
detect linked files
   |
offer "Open as collection"
   |
user approves root
```

---

# 36. Collection Root

A trusted collection root may permit:

- relative Markdown links,
- local images,
- cross-file search.

It should not grant:

- writes everywhere,
- execution,
- arbitrary traversal above root.

---

# 37. Broken Link Safety

Broken local links should result in:

```text
target not found
```

not fallback behavior that searches arbitrary filesystem locations without permission.

---

# 38. Plugin / Extension Security

If plugins are ever supported, they represent a major trust expansion.

Plugins may potentially access:

- document data,
- filesystem,
- network,
- UI,
- commands.

A future plugin system should define:

- manifest,
- permissions,
- signature/provenance,
- sandboxing,
- capability grants,
- update model.

Do not expose unrestricted Node execution by default.

---

# 39. Extension Permission Model

Possible future permissions:

```text
read-current-document
write-current-document
read-collection
network
clipboard
commands
ui-panel
```

Permissions should be explicit.

---

# 40. Third-Party Markdown Extensions

Syntax extensions should be treated separately from executable plugins.

A parser extension that only parses syntax is lower risk than a plugin that runs arbitrary code.

---

# 41. Mermaid / Diagram Rendering

Diagram renderers may introduce:

- HTML,
- SVG,
- external URLs,
- scriptable content.

Renderer must be configured in strict/safe mode.

Diagrams should not execute arbitrary JavaScript.

---

# 42. Math Rendering

Math libraries should be kept updated and configured without unsafe HTML execution where possible.

---

# 43. Preview Webviews / Iframes

Avoid using unrestricted Electron `<webview>` for Markdown preview.

If iframe-like isolation is needed:

- sandbox it,
- use restrictive CSP,
- prohibit Node integration,
- constrain navigation.

---

# 44. Content Security Policy

The renderer should define a restrictive Content Security Policy.

Conceptual goals:

```text
default-src 'self'
script-src 'self'
object-src 'none'
frame-src restricted
img-src controlled sources
style-src controlled policy
connect-src restricted
```

Exact CSP depends on bundler/runtime requirements.

Avoid broad:

```text
'unsafe-eval'
*
```

without compelling justification.

---

# 45. Development vs Production CSP

Development tooling may require looser policies.

Production builds should use stricter CSP.

Do not accidentally ship development CSP settings.

---

# 46. DevTools

Production behavior should consider whether arbitrary DevTools access matters for threat model.

DevTools are usually a local-user capability, not a document capability, but the app should not expose privileged secrets to renderer globals.

---

# 47. Dependency Security

The project should monitor:

- Electron,
- React,
- parser,
- sanitizer,
- editor engine,
- syntax highlighter,
- Mermaid/math libraries.

Requirements:

- lock dependencies,
- review security advisories,
- avoid abandoned security-critical packages,
- minimize dependency count where practical.

---

# 48. Supply Chain

Risks include:

- compromised npm package,
- malicious transitive dependency,
- build-script execution.

Mitigations:

- lockfile,
- dependency review,
- reproducible CI,
- restricted publish permissions,
- automated dependency alerts,
- avoid unnecessary install scripts.

---

# 49. Auto-Update Security

If auto-update is added later:

- updates must be signed,
- transport must be authenticated,
- update source must be trusted,
- rollback/downgrade behavior should be considered.

This is outside core reading but important for distribution.

---

# 50. Code Signing

Production releases should use platform code signing where practical.

Benefits include:

- integrity,
- reduced tampering warnings,
- trusted update flows.

---

# 51. Crash Reports and Telemetry

If telemetry is ever added:

- opt-in or clearly disclosed,
- minimize collected data,
- never include document text by default,
- scrub local paths where possible,
- document retention.

Core application should function without telemetry.

---

# 52. Logs

Logs should not routinely contain:

- full document text,
- clipboard contents,
- secrets,
- complete sensitive paths unnecessarily.

Debug logs may include node IDs and error context without dumping entire files.

---

# 53. Search Index Privacy

If search index is persisted:

- understand it may contain document text,
- store locally,
- protect from unintended upload,
- consider encrypting if broader app threat model later requires it.

Prefer recomputation unless persistence gives meaningful benefit.

---

# 54. Temporary Files

If temporary files are used:

- use OS-safe temp directory,
- unique names,
- restrictive permissions where possible,
- clean up,
- avoid predictable names.

---

# 55. Backup / Recovery Files

Autosave or crash-recovery data may contain sensitive document text.

Requirements:

- local only,
- documented location,
- lifecycle/cleanup,
- user control where practical.

---

# 56. Markdown Denial of Service

Malicious Markdown can attempt to cause:

- extremely deep nesting,
- huge tables,
- enormous inline strings,
- pathological parser behavior,
- huge embedded data URLs,
- giant diagrams.

The application should enforce practical resource limits.

---

# 57. Resource Limits

Potential limits:

```text
max parse recursion depth
max extension block size
max rendered image dimensions
max data URL size
max diagram complexity
max table cell count before fallback
```

Limits should fail gracefully.

---

# 58. Large File Handling

Huge files should not freeze the application indefinitely.

Possible mitigations:

- worker threads/web workers,
- incremental parsing,
- cancellation,
- progress indication,
- continuous-mode fallback.

---

# 59. Regex Safety

Avoid catastrophic backtracking in custom analysis rules.

Accessibility and search rules should use bounded or safe regex patterns.

Untrusted Markdown should never be able to trigger uncontrolled regex CPU usage.

---

# 60. HTML Entity / Unicode Abuse

Parser and renderer should handle:

- malformed entities,
- bidirectional control characters,
- invisible characters,
- Unicode confusables.

At minimum, they should not crash or execute code.

Optional future diagnostics may flag deceptive bidi/control characters in source.

---

# 61. Bidirectional Text Security

Source code blocks containing bidi controls can visually misrepresent logic.

For developer-focused reading, consider an optional warning for suspicious Unicode bidi controls in code blocks.

This is informational/security-oriented, not a Markdown accessibility requirement.

---

# 62. File Type Validation

Opening should primarily support Markdown.

Do not trust extension alone.

However, content sniffing should not create unsafe behavior.

Unknown/binary files should fail safely.

---

# 63. Save Safety

Before overwriting:

- ensure path matches intended document,
- handle external modification conflicts,
- preserve unsaved buffer on failure,
- avoid partial writes where possible.

Use atomic-write strategy where practical:

```text
write temp
fsync/close
rename
```

Platform-specific details may vary.

---

# 64. External Modification Race

File may change between:

```text
check
write
```

Conflict detection should use metadata/hash where appropriate.

Do not silently overwrite known external changes.

---

# 65. Path Normalization

All filesystem paths should be normalized using platform-aware APIs.

Do not compare security boundaries using naive string-prefix checks alone.

---

# 66. Windows Path Edge Cases

Consider:

- drive letters,
- UNC paths,
- alternate separators,
- reserved names,
- case-insensitivity,
- junctions/reparse points.

---

# 67. macOS Path Edge Cases

Consider:

- symlinks,
- normalization differences,
- sandbox/bookmark behavior if App Store distribution is ever used.

---

# 68. Linux Path Edge Cases

Consider:

- symlinks,
- case-sensitive paths,
- mount boundaries,
- desktop portal environments.

---

# 69. Link Preview Security

If a future link-preview feature fetches metadata:

- network request must be explicit,
- do not fetch local/private network URLs blindly,
- protect against SSRF.

---

# 70. SSRF

Any feature fetching URLs can be abused to reach:

```text
localhost
127.0.0.1
169.254.169.254
private RFC1918 ranges
internal services
```

A desktop app may have access to sensitive local services.

Network-fetch features should restrict destinations.

---

# 71. Localhost Links

Opening a localhost URL in external browser is different from fetching it inside the app.

Internal fetch capability should be more restricted.

---

# 72. Custom Protocols

Do not blindly launch arbitrary custom schemes.

Examples:

```text
vscode:
steam:
ssh:
file:
```

Potential policy:

- allow only known safe schemes,
- ask user,
- or open externally with warning.

---

# 73. Mailto Links

`mailto:` may be allowed, but user activation should be explicit.

Do not auto-trigger.

---

# 74. File Links

`file:` links need special handling.

The app should not permit a document to silently open arbitrary local files.

Possible policy:

- allow links within approved collection root,
- otherwise require user confirmation.

---

# 75. CSP for Document Content

If rendered Markdown shares the renderer DOM, ensure document content cannot inject:

- script tags,
- event handlers,
- remote frames,
- executable URLs.

Sanitization and CSP should be layered defenses.

---

# 76. DOM Clobbering

Untrusted HTML can attempt to create elements with IDs/names that interfere with JS assumptions.

Application code should avoid relying on global DOM-name resolution.

Use scoped React refs and explicit queries.

---

# 77. CSS Selector Collisions

Document classes/IDs should not collide with app UI.

Use scoped class naming or isolated rendering root.

---

# 78. XSS Regression Testing

Maintain malicious fixture documents containing:

```html
<script>alert(1)</script>
<img src=x onerror=alert(1)>
<a href="javascript:alert(1)">x</a>
<svg onload=alert(1)>
```

Expected:

- no execution,
- safe fallback/rendering.

---

# 79. Path Traversal Regression Testing

Fixtures should include:

```text
../../secret.txt
..\..\secret.txt
symlink-outside-root
absolute paths
UNC paths
```

Expected:

- access denied unless explicitly authorized.

---

# 80. Remote Resource Regression Testing

Fixture:

```md
![remote](https://example.invalid/pixel.png)
```

Expected behavior should match configured privacy policy.

# 82. Threat Scenarios

## THREAT-001 — Malicious README executes code

Attacker publishes repository with embedded HTML.

User opens README.

Desired outcome:

- HTML sanitized,
- no script execution,
- no Node access,
- no privileged IPC.

---

## THREAT-002 — Markdown steals SSH key through image path

Document references:

```text
../../.ssh/id_rsa
```

Desired outcome:

- renderer cannot load arbitrary file,
- local asset policy rejects outside allowed root.

---

## THREAT-003 — Tracking pixel

Document embeds remote image.

Desired outcome:

- behavior follows explicit remote-content policy,
- no silent hidden network request if policy blocks it.

---

## THREAT-004 — Link launches command

Document uses malicious URL scheme.

Desired outcome:

- scheme validation blocks unsafe launch.

---

## THREAT-005 — Custom CSS hides security prompt

Document stylesheet targets application button/dialog.

Desired outcome:

- document CSS is isolated from privileged UI.

---

## THREAT-006 — Renderer abuses preload

Injected script calls broad preload method:

```text
readFile("/etc/passwd")
```

Desired outcome:

- no generic method exists,
- narrow API denies unauthorized paths.

---

## THREAT-007 — Malformed document freezes UI

Pathological nested Markdown triggers expensive parse/render.

Desired outcome:

- bounded processing,
- cancellation/fallback,
- no permanent app hang.

---

# 83. STRIDE Mapping

## Spoofing

Threats:

- deceptive link text,
- fake application controls inside rendered content.

Mitigation:

- visually and semantically distinguish document content from privileged UI,
- external-link behavior clear.

## Tampering

Threats:

- unauthorized file modification,
- settings corruption.

Mitigation:

- explicit write paths,
- validation,
- atomic save,
- conflict detection.

## Repudiation

Less central for local app, but logs should record security-relevant errors without leaking content.

## Information Disclosure

Threats:

- remote images,
- arbitrary local file reads,
- logs,
- telemetry.

Mitigation:

- resource policy,
- narrow filesystem scope,
- local-first privacy.

## Denial of Service

Threats:

- pathological Markdown,
- huge assets,
- expensive extensions.

Mitigation:

- limits,
- workers,
- cancellation.

## Elevation of Privilege

Threats:

- XSS to Node/Electron APIs,
- unsafe IPC,
- plugins.

Mitigation:

- context isolation,
- sandboxing,
- minimal preload,
- no node integration.

# 84. Security Requirements by Component

## Main Process

Must:

- validate IPC,
- own privileged APIs,
- normalize paths,
- handle safe external opening.

## Preload

Must:

- expose narrow capability methods,
- avoid raw IPC exposure,
- avoid generic filesystem APIs.

## Renderer

Must:

- operate without Node privileges,
- treat Markdown as untrusted,
- use sanitized output.

## Markdown Renderer

Must:

- sanitize HTML,
- validate URLs,
- restrict remote content,
- isolate CSS.

## Editor

Must:

- preserve source,
- prevent accidental destructive writes,
- handle conflicts.

---

# 85. Security Definition of Done for Features

Any feature involving:

- files,
- URLs,
- HTML,
- CSS,
- external resources,
- IPC,
- plugins,
- shell integration,

must answer:

```text
What data crosses a trust boundary?
Who controls the input?
What privilege does the receiver have?
How is the input validated?
What happens on malformed input?
Can this cause a network request?
Can this cause a filesystem read/write?
Can this execute code?
Can this affect privileged UI?
```

---

# 86. Security Release Blockers

A release should be blocked for:

- renderer Node access,
- executable script from Markdown,
- arbitrary file reads triggered by document content,
- arbitrary shell execution,
- unvalidated privileged IPC,
- unsafe external URL schemes,
- custom CSS affecting privileged UI,
- silent overwrite of externally changed files,
- known high-severity dependency vulnerability in core security boundary.

---

- unit tests,

- dependency scanning,

- manual threat review,
- Electron configuration checks.

Security testing should be part of CI where practical.

# 89. Contributor Security Checklist

Before merging security-sensitive code:

- [ ] Is input user-controlled?
- [ ] Is input document-controlled?
- [ ] Does this cross renderer/main boundary?
- [ ] Is IPC schema validated?
- [ ] Are paths normalized?
- [ ] Are symlinks considered?
- [ ] Are URL schemes validated?
- [ ] Can this trigger network access?
- [ ] Can this read arbitrary local files?
- [ ] Can this write arbitrary local files?

# 90. Open Security Questions

1. Should remote images be blocked by default?
2. Should local assets be restricted to the document directory or collection root?
3. Should `file:` links outside collection roots require confirmation?
4. Should embedded HTML be enabled by default or opt-in?
5. Should SVG be sanitized or rendered only as inert image data?
6. How should custom CSS be sandboxed?
7. Should CSS `url()` be allowed for local assets only?
8. What sanitizer/library best fits the React/Electron stack?
9. Should book collections establish explicit trusted roots?
10. Should recovery/autosave files be encrypted at rest?
11. How much security logging is useful without exposing document content?
12. What plugin architecture could preserve least privilege if plugins are ever added?
13. Should remote link previews be omitted entirely to avoid SSRF/privacy complexity?
14. What CSP works with Vite production builds without weakening security?
15. What Electron sandbox settings are compatible with chosen editor/parser libraries?
16. How should App Store sandboxing affect macOS file access if distributed there?
17. Should documents downloaded from the internet receive a stricter trust profile?

# 91. Architectural Principle

The secure flow should remain:

```text
Untrusted Markdown
      |
      v
Parser
      |
      v
Semantic Model
      |
      v
Sanitized Renderer
      |
      v
Unprivileged React UI
      |
      v
Narrow Preload Capabilities
      |
      v
Validated Main-Process Operations
```

Never:

```text
Untrusted Markdown
      |
      v
Privileged Node/Electron API
```

---

# 92. Final Security Rule

> **Opening a Markdown file should never be equivalent to executing a program.**

The application should preserve the flexibility of Markdown while keeping document content firmly separated from application privilege.
