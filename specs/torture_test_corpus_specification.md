# Accessible Markdown Reader & Editor
# Torture-Test Corpus Specification

**Document type:** Test data and adversarial fixture specification  
**Status:** Working specification  
**Purpose:** Define the synthetic Markdown corpus used to stress semantic parsing, rendering, accessibility, navigation, pagination, search, editing, security, filesystem behavior, performance, and source fidelity.

---

# 1. Purpose

The application should not be tested only on clean, short, well-formed Markdown.

Real-world Markdown can be:

- huge,
- deeply nested,
- inconsistent,
- malformed,
- code-heavy,
- table-heavy,
- image-heavy,
- generated by tools,
- full of Unicode,
- linked across many files,
- accessibility-poor,
- security-hostile.

This corpus exists to deliberately stress the application.

The guiding principle is:

> **If the application is going to fail, we want it to fail first on files we designed to break it rather than on a user's document.**

---

# 2. Corpus Goals

The corpus should validate:

- parser robustness,
- semantic-model correctness,
- source-range fidelity,
- node identity,
- reading-position recovery,
- search quality,
- pagination,
- structural editing,
- accessibility analysis,
- screen-reader behavior,
- low-vision reflow,
- security boundaries,
- file/link resolution,
- performance,
- memory stability,
- source preservation.

# 4. Fixture Naming

Use descriptive names.

Examples:

```text
baseline-basic.md
semantic-duplicate-headings.md
pagination-giant-code-block.md
security-path-traversal.md
performance-10000-lines.md
```

Avoid opaque names such as:

```text

thing.md
sample-final2.md
```

---

# 5. Fixture Metadata

Each significant fixture should have metadata in a nearby README or manifest.

Example:

```json
{
  "id": "PERF-LONG-001",
  "file": "performance-10000-lines.md",
  "purpose": "Stress large-document parsing/search/navigation",
  "expectedLines": 10000,
  "expectedHeadings": 250,
  "expectedParagraphs": 2000
}
```

---

# 6. Reproducibility

Generated fixtures should have deterministic generators.

Record:

```text
generator version
random seed
target size
content parameters
```

A fixture should not silently change between runs.

Tests migrations.

# 80. CSP / HTML Security Fixture

Document includes every prohibited construct in one file.

Expected:

- inert/sanitized output,
- app remains usable.

---

# 81. Denial-of-Service Fixture Policy

Stress files should be large enough to reveal poor algorithms but not intentionally damage developer/test machines.

Extreme cases should run only in:

```text
stress suite
```

not routine unit tests.

---

# 82. Corpus Test Levels

## Level 1 — Fast

Small deterministic fixtures.

Runs on every PR.

## Level 2 — Standard

Medium/large fixtures.

Runs in normal CI.

## Level 3 — Stress

Huge/pathological fixtures.

Runs scheduled/nightly/release.

## Level 4 — Manual AT

Fixtures designed for human assistive-technology validation.

# 83. CI Corpus Selection

PR suite:

```text
baseline
semantic
small search
small pagination

security smoke
```

Nightly:

```text
large search
100-chapter book
large pagination

```

# 84. Expected Failure Policy

A fixture may intentionally exceed supported limits.

Expected result must be explicit.

Example:

```text
50 MB pathological file
```

Expected:

```text
opens in degraded continuous mode
pagination disabled
no crash
```

Not:

```text
must fully paginate instantly
```

---

# 85. Corpus Versioning

The corpus should have its own version.

Example:

```text
corpusVersion: 1
```

Benchmark results should record corpus version.

---

# 86. Fixture Stability

Do not casually modify a benchmark fixture in place.

Changes alter performance baselines.

Prefer:

```text
performance-10000-lines-v2.md
```

or update corpus version with clear note.

# 89. Contributor Rule

When fixing a bug caused by a document shape not already represented:

> Add or extend a fixture that reproduces the document shape.

This turns user-discovered edge cases into permanent coverage.

---

# 90. Sanitization of User Bugs

If a real user's document reveals a defect:

- do not commit their private document,
- create a synthetic minimal reproduction,
- preserve the structural trigger,
- remove personal content.

---

# 91. Corpus Generator Quality

Generators should:

- produce valid intended structure,
- validate counts,
- be deterministic,
- fail clearly.

Generated fixture tests may assert expected counts.

# 94. Definition of Done

The torture-test corpus should eventually be considered mature when it includes:

- basic Markdown,
- semantic edge cases,
- large documents,
- huge code blocks,
- huge tables,
- image/link failures,
- multi-file books,
- search stress,
- reading-position mutations,
- accessibility-good and accessibility-bad fixtures,
- Unicode/RTL,
- malformed Markdown,
- security-hostile content,
- filesystem edge cases,
- source-fidelity variants,
- schema migration fixtures,
- deterministic generators,
- documented expected failures.

---

# 95. Core Testing Rule

> **Every important assumption about Markdown should have a file somewhere in the corpus that tries to prove the assumption wrong.**
